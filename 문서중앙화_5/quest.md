# DLP 서비스 고도화를 위한 추가 고려사항

본 문서는 현재 DLP(Data Loss Prevention) 서비스의 아키텍처를 한 단계 더 발전시키기 위해 고민해볼 만한 기술적, 정책적 질문들을 정리한 것입니다.

---

### 1. 대용량 파일 처리 및 성능

- **메모리 사용량:** 현재 구현은 파일 전체를 메모리에 로드합니다. 만약 수백 MB 이상의 대용량 파일을 처리해야 할 경우, 메모리 부족(OOM)이 발생할 수 있습니다.
  - **고민해볼 점:** 파일을 스트림(Stream)으로 읽고 처리하여 메모리 사용량을 일정하게 유지하는 구조로 개선할 수 있을까요?

- **동시성 및 부하:** 수많은 요청이 동시에 들어올 경우, 서버에 과부하가 걸리거나 응답 시간이 길어질 수 있습니다.
  - **고민해볼 점:** 요청을 메시지 큐(Message Queue)에 쌓아두고, 별도의 워커(Worker)가 순차적으로 처리하는 비동기 아키텍처를 도입해야 할까요?

---

### 2. 다양한 파일 형식 지원

- **비-텍스트 파일 처리:** 현재 서비스는 텍스트 파일 처리에 중점을 두고 있습니다. 이미지(`.jpg`, `.png`), PDF, MS Office 문서(`.docx`, `.xlsx`) 등 다양한 파일 형식 안에 포함된 민감 정보를 어떻게 탐지할 수 있을까요?
  - **고민해볼 점:** 파일의 종류(MIME Type)를 먼저 식별하고, 파일 형식에 맞는 처리기(텍스트 파서, 이미지 OCR, PDF 파서 등)로 동적으로 라우팅하는 구조를 설계해야 하지 않을까요?

---

### 3. 규칙 관리의 유연성

- **실시간 규칙 업데이트:** 현재는 규칙을 변경하려면 `YAML` 파일을 수정하고 서비스를 재배포해야 합니다.
  - **고민해볼 점:** 서비스를 중단하지 않고 실시간으로 탐지 규칙을 추가/수정/삭제할 수 있는 방법은 무엇일까요? 데이터베이스나 외부 설정 저장소(Etcd, Consul 등)와 연동하고, 관리자용 UI를 제공하는 방안을 고려해볼 수 있습니다. (현재 `Repository` 패턴은 이러한 확장에 매우 유리한 구조입니다.)

---

### 4. 탐지 정확도 및 예외 처리

- **오탐(False Positives) 감소:** "주민등록번호 예시: 123456-1234567"과 같이 실제 민감 데이터가 아닌 경우도 탐지될 수 있습니다.
  - **고민해볼 점:** 특정 키워드('예시', '샘플' 등)가 주변에 있을 때 탐지에서 제외하거나, 특정 패턴을 무시하는 예외 목록(Allowlist)을 어떻게 관리할 수 있을까요?

- **탐지 결과 로깅 정책:** 탐지된 민감 데이터를 로그 파일에 그대로 기록하면, 해당 로그가 2차 보안 유출 경로가 될 수 있습니다.
  - **고민해볼 점:** 어떤 내용을 로그로 남겨야 할까요? "SSN_PATTERN 패턴 3회 탐지"와 같이 실제 데이터가 아닌 메타데이터만 기록하는 정책을 수립해야 하지 않을까요?

---

### 5. 아키텍처: 클라이언트와 서버의 역할

- **문서 변경 감지 주체:** 문서의 변경을 누가, 어떻게 감지하여 서버에 전달할 것인가?
  - **고민해볼 점:**
    - **실시간성:** 사용자의 수정 즉시 탐지가 필요하다면, 클라이언트(에이전트, 편집기 플러그인 등)가 변경을 감지하여 서버에 알리는 구조가 필수적입니다.
    - **정합성:** 클라이언트의 알림 누락을 대비하여, 서버가 주기적으로 전체 문서를 스캔하는 배치(Batch) 작업을 병행해야 할까요? 두 방식의 장단점과 역할 분담을 어떻게 정의해야 할까요?

---

### 6. 데이터 전송 형식

- **API 데이터 모델:** 클라이언트가 서버로 데이터를 전송할 때 어떤 형식을 사용해야 하는가?
  - **고민해볼 점:**
    - **`byte[]`:** 파일의 인코딩 문제로부터 자유롭고, 텍스트가 아닌 파일(이미지, PDF 등)까지 포괄적으로 지원할 수 있는 장점이 있습니다. 파일 업로드와 같은 기능에 적합합니다.
    - **`String`:** JSON 본문에 텍스트를 직접 담아 보내는 방식으로, API 명세가 단순하고 직관적입니다. 문서의 일부 변경분(diff)을 전송하는 등, 텍스트 조각을 다룰 때 편리합니다.
    - 두 방식을 어떻게 조합하여 유연하고 안정적인 API를 설계할 수 있을까요?
